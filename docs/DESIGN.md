# slop-compost — 슬롭을 다음 아이디어의 거름으로 (설계 v0.3)

> 상태: v0.1 구현 · 작성 2026-10-15 · 개정 2026-10-15 (아래 "v0.2 변경점", "v0.3 변경점")
>
> 실패는 성공의 어머니. 슬롭(실패작)은 버릴 쓰레기가 아니라 다음 아이디어의 거름이다.

## 한 줄

만들다 멈춘 결과물(코드·글·아이디어)을 모아 **쓸 만한 부품과 교훈**을 뽑고, **두 트랙**(현재 아이디어를 살리는 길 / 새 아이디어로 가는 길)으로 방향을 제시한다. 사용자의 판단이 장부에 쌓여 다음 실행이 그 사람에게 더 맞게 된다.

## 누구를 위한가

- 1차: 작성자 본인(테스트베드). 2차: 바이브코딩으로 결과물을 찍어내는 누구나.
- 그래서 **처음 한 번 써도 가치가 있어야 하고**(장부가 비어 있어도 동작), **쓸수록 깊어져야 한다**(장부가 쌓이면 개인화).

## 원칙

1. **판단은 사용자가 한다.** 스킬은 방향 제시까지만 한다. 착수·구현은 하지 않는다.
2. **근거 없는 교훈 금지.** 모든 교훈은 결과물 안의 근거 위치(파일:줄, 문단, 메모 줄)를 인용하고, 반증할 수 있는 한 문장으로 쓴다. "UX 개선 필요" 같은 문장은 거부한다.
3. **반대 증거를 강제한다.** 트랙 B는 외부 정보로 지지 근거만 모으지 않는다. 후보마다 "실패할 이유"와 "비슷하게 해서 망한 사례"를 함께 낸다.
4. **두 트랙은 항상 둘 다 나온다.** 사용자가 트랙을 고르지 않는다. 후보마다 따로 판단한다.
5. **지우지 않는다.** 기각한 후보, 이전 교훈, 이전 의도도 장부에 남긴다.
6. **시스템 규칙 변경은 승인을 거친다.** 분석 기준·출처 가중치·프롬프트를 고치자는 제안은 사용자가 승인한 것만 반영한다.
7. **수집은 하지 않는다.** 외부 데이터는 읽기만 한다. 수집기를 돌리는 건 별도 시스템의 일이고, 그 출력은 `local` 출처로 붙인다.
8. **스킬 자신의 슬롭도 퇴비다.** 버리지 않고 시스템 개선과 재료로 쓴다. "Reject if" 에 걸린 교훈·후보는 사용자 출력에서 빼고 `compost.jsonl` 에 저장한다.

## 흐름

```
0. 회상 ──────── 장부 읽기 + 지난 채택 후보 후속 확인
1. 입력 ──────── 폴더·저장소·텍스트 판별, 권한 막히면 안내
2. 분석 ──────── 결과물마다 부품 + 멈춘 이유, 결과물 사이 패턴
3. 교훈 ──────── 근거 위치 + 반증 가능한 한 문장
4. 의도 (선택) ── 내 생각·제약 입력, 지난 의도 유지 여부 확인
5. 두 트랙 ───── A: 현재 아이디어를 살린다면 / B: 새 아이디어로 간다면   (병렬, 서로 못 봄)
6. 방향 제시 ─── 트랙별 후보, 각각 첫 실험 + 성공 기준
7. 판단 ──────── 후보마다 채택 / 보류 / 기각 + 이유 한 줄
8. 기록 ──────── 장부 갱신, 개인 프로필 갱신, 시스템 개선 제안
```

### 0. 회상 (`steps/00-recall.md`)
- 장부가 없으면 "첫 실행"으로 표시하고 건너뛴다. 첫 실행은 항상 `full` 모드다. 출처 목록(`sources.md`)을 기본값으로 시드한다.
- 답은 관대하게 파싱한다(7단계와 같은 규칙, 한국어 대응어 `손댔음/안 함`, `진행중/완료/중단`, `스킵` 허용).
- 지난 실행에서 **채택한 후보** 목록을 번호(F1, F2…)로 한 번에 보여 주고 **한 줄로 일괄** 답받는다: 손댔나 / 결과는 / 그만뒀다면 왜. 답은 `decisions.jsonl` 의 해당 후보 `followups` 에 붙인다.
- `skip`(또는 빠뜨린 항목)은 followup 을 남기지 않고 다음에 다시 묻는다. 단 `skip_count` 가 3회 연속이면 `stale` 표시 후 그만 묻는다.
- 반복 패턴 요약을 다음 단계로 넘긴다(예: "채택 5건 중 착수 1건", "같은 교훈 3회째").

### 1. 입력 (`steps/01-intake.md`)
- 받는 것: 로컬 폴더 경로, git 참조 `<repo>@<branch>:<path>`(fetch 없이 있는 ref 를 읽음, 지문 = `git rev-parse <branch>:<path>`), GitHub 저장소 URL, Notion 페이지, 자유 텍스트("이런 거 만들다 말았어"). 섞어서 받는다.
- **실행 범위**는 이번 입력의 결과물이다. 장부에만 있는 결과물은 재분석하지 않는다(부품은 트랙 B 가 `parts.jsonl` 에서 쓴다).
- 로컬 폴더 지문은 2단계와 같은 파일 필터를 쓴다: `.venv venv .next dist build __pycache__ .omc .claude logs node_modules` 디렉터리와 `*.db* *.sqlite* *.lock` 파일을 빼고, 소스·문서 확장자만 해시한다.
- 결과물마다 유형을 판별한다: `code` / `writing` / `idea` (혼합이면 주 유형 하나 + 보조 유형).
- 장부에 이미 있는 결과물이면 변경분만 본다(아래 "증분 분석").
- 결과물이 **10개를 넘으면** 한 번에 분석할지 먼저 묻는다(비용 가드).
- **권한 막힘 처리**: 실패한 그 자리에서 실행할 명령 한 줄을 안내하고, 나머지 결과물로 계속 진행한다.

| 입력 | 막히는 경우 | 안내 |
|---|---|---|
| 비공개 GitHub | 인증 없음 | `! gh auth login` |
| Notion | MCP 미연결 | Notion MCP 연결 방법 + 대안: 페이지를 마크다운으로 내보내 폴더로 넣기 |
| 로컬 폴더 | 경로 없음·권한 | 경로 확인, `ls -la` 결과로 원인 안내 |
| 기타 URL | 로그인 필요 | 내보내기 파일로 넣기 |

### 2. 분석 (`steps/02-analyze.md` + `rubrics/{code,writing,idea}.md`)
결과물마다:
- **요약**: 무엇을 하려 했나, 어디까지 갔나(완성도).
- **부품**: 다시 쓸 수 있는 조각. 종류(모듈·문장·문제 정의·데이터·디자인), 위치, 왜 쓸 만한지.
- **비용 가드**: 결과물당 핵심 파일 **50개** 상한(진입점·README·설정·최근 변경 순). 상한에 걸리면 `partial` 표시.
- **DB 는 제자리에서 열지 않는다**: 작업 폴더로 복사해 조회하거나 `file:<path>?immutable=1`. `-readonly` 도 `-shm` 을 건드린다.
- **멈춘 이유**: 사용자가 고른다(스킬이 근거와 함께 추정값을 제시하고, 모든 결과물을 한 번에 한 줄로 확인·수정받는다. 빈 답이면 추정값을 `accepted-guess` 로 기록). 모든 값 뒤에 `"메모"` 를 붙일 수 있고 카드 front-matter `stop_reason_notes` 에 남는다. `no-revenue`(돈을 못 벌었다) / `unfinished`(완성을 못 했다) / `abandoned`(만들고 버렸다) / `other`. 여러 개를 골라도 된다.

결과물 사이:
- **반복 주제**: 여러 결과물이 같은 문제를 건드리면 표시한다 → 부활 우선순위가 오른다.
- **반복 행동**: 예) "검증 전에 기능 7개", "랜딩 없이 백엔드부터".
- 패턴에는 장부의 기존 결과물도 `(ledger)` 표시로 넣을 수 있다.

### 3. 교훈 (`steps/03-lessons.md`)
- 형식은 `templates/lesson.md`: 한 문장 + 근거 위치 + 반증 조건 + 관련 멈춘 이유.
- 장부의 이전 교훈과 비교해 **반복 횟수**를 센다. 3회 이상이면 "구조적 습관"으로 올린다.
- 원인 교훈("맥락이 없어서 결과가 뻔했다")과 반응 교훈("품질이 실망스러우면 고쳐 보기 전에 접는다")은 같은 실패를 다뤄도 별개 교훈이다.

### 4. 의도 — 선택 (`steps/04-intent.md`)
- 사용자가 생각·제약을 넣는다. 예) "B2B만", "이 부품은 꼭 살리고 싶다", "월 10만 원 이하 운영비".
- 장부에 이전 의도가 있으면 먼저 묻는다: "지난번 'B2B만'을 유지할까요?"
- 건너뛰어도 된다. 입력한 의도는 트랙 A·B 모두에 들어간다.

### 5. 두 트랙 (`steps/05a-track-revive.md`, `steps/05b-track-new.md`)
오케스트레이터가 **두 서브에이전트를 병렬로**(Agent 도구, 한 메시지에서 동시에) 띄운다. 서로의 결과를 보지 못하게 한다(독립성). 입력은 트랙별 번들 파일(`input-a.md`, `input-b.md`)로 나눈다.

트랙 B 입력(`input-b.md`)에서는 프로필·기각 이유 중 트랙 A 라벨·내용을 언급한 문장을 일반화하거나 뺀다(예: "A1이랑 겹침" → "다른 후보와 중복"). 트랙 파일에는 퇴비 후보의 내용 없이 건수만 남긴다.

5단계 시작 전에 예상 규모를 한 줄로 보여 준다(트랙 2개, 출처 N개). **경량 모드**: 증분 실행에서 새 결과물이 `idea`/`writing` 1개뿐이면 트랙 B 는 출처를 범주당 1개로 줄인다.

서브에이전트를 못 쓰는 환경이면: A 를 먼저 쓰고 출력을 고정한 뒤 B 를 쓴다. B 작성 중에는 A 를 참조하지 않는다. run 기록에 `fallback: sequential` 을 남긴다.

| | 트랙 A: 현재 아이디어를 살린다면 | 트랙 B: 새 아이디어로 간다면 |
|---|---|---|
| 입력 | 결과물 + 부품 + 교훈 + 의도 | 교훈 + 모든 결과물의 부품 + 의도 + **외부 정보** |
| 하는 일 | 멈춘 이유별 처방으로 원래 결과물을 고친다 | 부품 재조합 + 외부 신호로 새 아이디어를 만든다 |
| 필수 | 교훈마다 어떤 수정으로 이어지는지 | 후보마다 외부 근거(출처·날짜) + **반대 증거** |

멈춘 이유별 처방(트랙 A 기본값):
- `unfinished` → 범위를 줄인다. "남은 것 중 하나만 끝낸다면?"
- `no-revenue` → 대상 고객·가격·채널을 바꾼다.
- `abandoned` → 동기를 확인한다. 동기가 없으면 부품만 넘기고 원 결과물은 보내 준다.

### 6. 방향 제시 (`steps/06-direction.md`)
- 출력은 `templates/direction.md`. 두 트랙을 **나란히** 보여 준다: "현재 아이디어대로라면 이렇게 / 새 아이디어대로라면 이렇게".
- 트랙당 후보 1–3개. 후보마다:
  - 한 줄 정의, 쓰는 부품(출처 결과물), 근거 교훈
  - **첫 실험**(7일 안에 끝나는 크기) + **성공 기준**(숫자)
  - 트랙 B만: 외부 근거, 반대 증거
- **첫 실행 가치**: 장부가 비어도 "부품 목록 + 결과물 사이 패턴" 섹션을 반드시 낸다. 패턴 생략은 이번 결과물과 장부 결과물을 합쳐 1개일 때만.
- **수렴 표시**: 두 트랙이 같은 방향에 닿으면 병합하지 않고 `수렴: A1 ≈ B2` 한 줄을 붙인다. 독립 경로가 같은 결론에 닿은 것은 강한 신호다. 7단계에서 둘 중 하나를 고르라고 강요하지 않는다.
- 끝에 퇴비 요약 한 줄만: "퇴비로 보낸 것 N건 (규칙별 건수)". 내용은 사용자가 원할 때만 보여 준다.
- 출력은 장부의 `runs/<날짜>.md` 에도 저장한다.

### 7. 판단 (`steps/07-judge.md`)
- 후보마다 `adopt`(채택) / `hold`(보류) / `reject`(기각) + 이유 한 줄. 이유는 비워도 되지만 권한다.
- **일괄 입력**: 후보마다 묻지 않고 번호를 붙여 한 줄로 받는다. 예) `A1 adopt 이유..., A2 hold, B1 reject 운영부담` 또는 `A1 a, B2 r`. 빠진 후보·빈 답은 `hold`. 질문 피로를 줄이는 게 목적.
- 트랙을 고르라고 하지 않는다. 장부에는 후보의 트랙 꼬리표가 자동으로 붙는다.

### 8. 기록 (`steps/08-ledger.md`)
- `decisions.jsonl` 에 판단을 덧붙인다.
- `profile.md`(개인 프로필) 갱신: 취향(무엇을 채택·기각하나), 실행 패턴(채택 대비 착수율), 반복 교훈, 활성 의도. **근거 결정 id 인용 필수.**
- 시스템 개선 제안: 근거가 쌓였을 때만 `proposals.md` 에 덧붙인다(예: "트랙 B 후보 기각 사유 4건 중 3건이 '운영 부담' → 트랙 B에 운영비 추정 필수화"). 사용자가 승인한 것만 반영한다. 반영은 스킬 폴더를 고치지 않고 장부의 `overrides.md` 에 덧붙인다(대상 파일·규칙 id, 바뀐 지시, 근거 proposal id, 승인일). `proposals.md` 에는 `applied-to: overrides.md` 를 기록한다.
- 오케스트레이터는 시작할 때 `overrides.md` 가 있으면 읽고, 각 단계 파일을 읽을 때 그 단계의 override 를 파일 내용보다 우선 적용한다. 플러그인 업데이트로 지워지지 않는다.
- 업스트림 반영(선택): 사용자가 원하면 `export/overrides-<날짜>.md` 에 저장소 경로·규칙 id·diff 제안·횟수만 담은 이유를 개인 정보 없이 쓴다. PR 은 사용자가 직접 연다.
- **퇴비 핫스팟**: 같은 규칙에 걸린 퇴비가 여러 실행에 걸쳐 쌓이면(기본 3개 실행에서 5건 이상) "이 단계의 지시/루브릭을 고치자" 제안을 근거 퇴비 id 와 함께 `proposals.md` 에 남긴다. 승인 필요.

## 성장 루프 — 두 층

| 층 | 무엇이 바뀌나 | 근거 | 승인 |
|---|---|---|---|
| 개인 | `profile.md`, 의도, 반복 교훈 → 다음 추천의 우선순위 | 판단·후속 확인·의도 | 자동(기록일 뿐) |
| 시스템 | 루브릭, 처방, 출처 가중치, 템플릿 | 여러 실행에 걸친 판단 패턴 | **사용자 승인 필수** |

- 트랙 꼬리표 통계(트랙별 채택·착수율)는 시스템 층 근거로만 쓴다. 사용자에게 트랙 선택을 요구하지 않는다.
- 작성자의 다른 프로젝트에서 검증한 성장 루프 원칙을 따른다: 근거 없는 학습 금지, 변화는 작게, 지우지 않음, 규칙 변경은 승인.
- **출처 성과**: 트랙 B 근거마다 출처 id(`[src:<id>]`)를 남기고 판단과 조인해 `state.json.source_stats` 에 출처별 인용·채택 인용 수를 쌓는다. 최근 5회 실행 동안 채택 후보에 한 번도 인용되지 않은 출처는 "끌까요?" 제안(승인 필요)을 낸다.

## 증분 분석

- 평소: 새 결과물·변경분만 분석하고, 장부의 부품 목록과 대조한다.
- 전체 재분석: 사용자가 요청하거나, 마지막 전체 분석 이후 새 결과물이 **10개**(`SLOP_COMPOST_FULL_EVERY`) 쌓이면.
- 결과물 지문: 폴더는 git HEAD 또는 파일 해시, URL은 마지막 수정 시각, 텍스트는 내용 해시.

## 외부 정보 — 출처 목록 (`sources/defaults.md`, `sources/README.md`)

트랙 B만 쓴다. 기본 목록은 스킬에 동봉하고, 첫 실행(또는 파일이 없을 때) 장부의 `$LEDGER/sources.md` 로 복사한다. 이후에는 **사용자 목록이 기준**이다. 플러그인 업데이트로 기본값에 새 항목이 생기면 "새 기본 출처 N개 — 추가할까요?" 한 줄로만 제안한다.

항목 필드: `id`, `category`(trend | ai-trend | revenue | failure | community-ko), `type`(web | fetch | local), `how`(URL 또는 `{keyword}` 쿼리 템플릿), `limits`, `notes`, `enabled`. 공통 한도: 실행당 출처별 요청 1–2회.

| id | 범주 | 방식 | 비고 |
|---|---|---|---|
| hn-show | trend | fetch + web | HN Algolia Show HN API |
| github-trending | ai-trend | fetch | 주간 트렌딩 |
| hf-papers | ai-trend | fetch | 수요 근거로는 쓰지 않음 |
| trustmrr | revenue | fetch + web | 검증된 매출 수치 |
| failory | failure | fetch + web | 실패 스타트업 묘지·창업자 인터뷰·구글 종료 서비스. 상세 페이지의 Cause·Closed 필드를 반대 증거로 인용. robots 금지 경로 `/startup/` `/get/` `/author/` 만 피함. 목록 1 + 상세 최대 2 |
| failure-search | failure | web | 영어·한국어 종료 후기 검색, 후보마다 항상 |
| geeknews | community-ko | fetch + web | RSS 우선 |
| disquiet | community-ko | web | 한국 메이커 커뮤니티 |
| exploding-topics | trend | fetch + web | 상승 검색 주제 |

- 제외: Product Hunt(403, 토큰 API), Reddit(robots 전체 차단), Indie Hackers(403, 사용자가 선택으로 추가 가능), 구독 제한 사이트(유료 아이디어 뱅크 류).
- 한국 도메인은 WebSearch 결과가 빈약할 수 있으니 fetch 타입 URL(RSS 등)을 우선한다.
- 성공 사례만 넣으면 생존자 편향이 커진다 → 후보마다 `failure` 범주 출처를 최소 1개 쓴다.
- **`local` 타입**: 폴더 경로 또는 git 참조 `<repo>@<branch>:<path>`. `git fetch` 는 하지 않고 이미 있는 ref 를 `git show` / `ls-tree` 로 읽는다(오래됐으면 fetch 명령만 안내). JSON 항목 최소 필드 `title`, `summary`, `source_url`, `date`. 마크다운도 허용. 자기 수집기는 이걸로 붙인다.
- **CRUD**: `/slop-compost sources list|add|remove|edit|enable|disable [id]`. add 는 한 줄 대화로 type/how/category 를 받는다. remove 는 지우지 않고 `removed: <날짜>` 표시.
- **퇴비 재료**: 트랙 B 는 퇴비 중 "근거만 부족했던" 후보(`failed_rules` 가 근거 규칙 `.ev-` 뿐인 것)를 재료로 다시 볼 수 있다. 다시 쓰면 빠졌던 근거를 반드시 채우고, `reused_in` 에 run id 를 기록한다.

## 장부 (기본 `~/.slop-compost/`, `SLOP_COMPOST_HOME` 으로 변경)

```
~/.slop-compost/
├── artifacts/<id>.md      # 결과물 카드: 출처, 유형, 지문, 요약, 부품, 멈춘 이유
├── parts.jsonl            # 부품 색인(결과물 id, 종류, 위치, 설명)
├── lessons.md             # 교훈 누적(날짜 섹션, 반복 횟수)
├── intents.md             # 의도 이력(활성/종료)
├── decisions.jsonl        # 후보별 판단 + 트랙 꼬리표 + 후속 확인(skip_count, stale)
├── compost.jsonl          # "Reject if" 에 걸린 출력(퇴비): {id, run, step, kind(lesson|candidate|part|pattern|other), content, failed_rules, at, reused_in}
├── profile.md             # 개인 프로필(근거 id 인용)
├── proposals.md           # 시스템 개선 제안과 승인 여부
├── overrides.md           # 승인된 시스템 변경 (스킬 파일 위에 덧씌움)
├── sources.md             # 사용자 출처 목록 (기본값에서 시드)
├── runs/<YYYY-MM-DD>.md   # 실행별 방향 제시 원문 (+ runs/<run-id>.work/ 작업 파일)
├── state.json             # last_full_analysis, artifacts_since_full, 결과물 지문, source_stats
└── export/                # 공용 내보내기(아래)
```

## 공용 내보내기 — v1은 형식만

- v1은 개인 장부만 쓴다. 외부로 보내는 기능은 없다.
- `export/` 형식만 정해 둔다: 결과물 요약·멈춘 이유·교훈·판단을 **개인 정보와 코드 원문을 뺀** 형태로 담는다.
- 나중에 "공용 아이디어 묘지"를 만들 때 이 형식을 쓴다. 보낼 때는 사용자 동의를 매번 받는다.

## 스킬 파일 구조 (저장소 = 마켓플레이스 = 플러그인 루트)

```
slop-compost/
├── .claude-plugin/{marketplace.json, plugin.json}
├── skills/slop-compost/
│   ├── SKILL.md                # 오케스트레이터: 단계 순서, 공통 규칙, 트랙 병렬 실행, 장부 경로
│   ├── steps/00-recall.md … 08-ledger.md (05a, 05b 포함)
│   ├── rubrics/{code,writing,idea}.md
│   ├── sources/{README.md, defaults.md}
│   └── templates/{artifact,lesson,direction,profile,export}.md
├── docs/DESIGN.md
├── README.md, README.ko.md, LICENSE
```

- 오케스트레이터는 각 단계 파일을 **그 단계에 들어갈 때만** 읽는다(컨텍스트 절약). 경로는 `${CLAUDE_SKILL_DIR}` 기준(수동 설치·플러그인 설치 모두 동작).
- 트랙 A·B는 서브에이전트로 띄우고, 각 트랙 파일을 브리프로 넘긴다.
- 모든 step 파일은 `Inputs / Do / Output / Reject if` 섹션을 가진다. "Reject if" 항목은 규칙 id(`03.ev-no-location` 등)를 가지며, `.ev-` 가 들어간 id 는 근거 규칙이다.

## v1 범위

## 테스트베드 (첫 실행 재료)

- 작성자의 하다 만 프로젝트들: 뉴스 아이디어 생성기 등 실패작(코드), 기각해 둔 아이디어 메모, 자유 텍스트로 적은 접은 아이디어 몇 개.
- 결과: 2회 실행(전체 1회 + 증분 1회)으로 장부 생성, 0단계 후속 확인, 증분 분석, 반복 교훈 판정이 동작함을 확인했다. 실측 약 43만 토큰(1회 약 8분).

완료 기준: 위 재료로 0–8을 한 번 돌려 장부가 생기고, 두 번째 실행에서 0단계 후속 확인과 증분 분석이 동작한다.

## v0.2 변경점 (2026-10-15)

- 이름: 가칭에서 `slop-compost` 로 확정. 장부 `~/.slop-compost/`, 환경변수 접두어 `SLOP_COMPOST_`. 호출: 플러그인 `/slop-compost:slop-compost`, 수동 설치 `/slop-compost`.
- 언어: 스킬 지시문은 영어. 사용자 언어를 감지해 출력·질문·장부 본문을 그 언어로 쓴다(`SLOP_COMPOST_LANG=ko|en` 로 강제). JSONL 키·enum 값은 영어 고정.
- 판단(7단계)·후속 확인(0단계)·멈춘 이유 확인(2단계)은 모두 한 줄 일괄 입력.
- 첫 실행에도 부품 목록 + 결과물 사이 패턴을 낸다.
- 비용 가드: 결과물당 핵심 파일 50개, 결과물 10개 초과 시 먼저 확인.
- 슬롭 방지 출력 규칙: 근거 위치 없는 교훈, 첫 실험(7일 이내)+숫자 성공 기준 없는 후보, 외부 근거(출처+날짜)·반대 증거 없는 트랙 B 후보는 퇴비로 보낸다.
- 퇴비(`compost.jsonl`): 시스템 층(규칙 핫스팟 → 개선 제안)과 재료 층(트랙 B 재사용) 두 쓰임새.
- 트랙 A/B 병렬 서브에이전트, 불가 시 순차 폴백.
- 승인된 시스템 개선은 스킬 폴더가 아니라 장부 `overrides.md` 에 쌓는다. 업스트림 PR 용 내보내기 형식(파일·diff 제안)을 둔다.

## v0.3 변경점 (2026-10-15)
